# Claim-anchored research: tag syntax, strictness, where checks live

Decision document for task `B-rw-decide`, filed by `P-decisions-docs.write`. It restates the decision records below; the records in the event log are the source of truth (`ddflow decision show <id>`).

## D-research-system: Research as claims anchored to code: revision-pinned comment tags, checks that live in the repo's tests, warn by default and block per claim, built on the shared components

status **accepted** · decided by operator · decided by opus-lead

**Decision.** Operator 2026-10-08 (answers to three questions) and design from R-research-system. (1) A research record holds atomic CLAIMS (kinds formula, algorithm, constant, protocol, behaviour, fact), stored as def-records of kind 'claim' with an upcaster from research.recorded; each claim has a revision, a structured subject/attribute/value/unit/conditions where it applies, sources with quoted passage, locator, content hash and retrieval date, an evidence grade, a validity window, and links to code anchors, tests and decisions. (2) Code references a claim with a plain comment tag in any language, pinned to a revision: '# ddflow: implements C-xxxx@N' (the code is the claim) or '# ddflow: uses C-xxxx@N' (it relies on it), resolved to the next function or class, with an optional commit trailer 'Implements: C-xxxx@N'. A claim revised past N makes the tag 'outdated'; a changed tagged symbol is classified trivial (comment, whitespace, rename: re-pinned) or substantive (re-verify); a removed tag or symbol makes the claim an orphan. (3) A claim's executable checks live in the repository's tests (named test ids; known-answer vectors, property, oracle, metamorphic and doctest checks stay in git); a bare shell-command check proposed by an agent is inert until the operator approves its digest; checks run through the shared command runner and an unrunnable check is 'unavailable', never passed. (4) Enforcement is warn by default and block per claim: uncited implementations and failed or unrunnable checks are shown at the gate, in brief and in review prompts; a claim set to block fails the gate. (5) Relevant claims reach every context through the one context pack: brief and claim, implement and review gate prompts, edit time (a hook keyed on the file being edited: anchored claims first, fuzzy hits after), claim time (neighbours for the duplicate and contradiction check) and MCP; exact anchors always outrank fuzzy hits. (6) Duplicates and contradictions are checked per claim: structured same-subject-and-attribute with a different value after unit normalisation is an exact contradiction; a new REFUTED against a live CONFIRMED, polarity and number conflicts are flagged and block CONFIRMED until resolved; nothing is deleted: revise bumps the revision, supersede sets validity, REFUTED flags every anchored code site as a suspected bug. (7) Every part reuses a P-unify component: def-records, upcasters, search-core, context-pack, change detector, command runner, approval, overlay loader, record surface, kind-pipeline predicates, guidance engine.

Governs: `ddflow/services/research/**`, `ddflow/core/defs.py`, `ddflow/api/knowledge/research.py`

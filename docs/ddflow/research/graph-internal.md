# ddflow: graphs it already has, and where one is missing (internal audit)

Measured on this repo, 2026-10-19: 2735 items (2527 tasks, 131 phases), 4547 `needs` edges, 256 decisions,
113 lessons, 532 link entries, event log 65 MB. Numbers below are mine (cProfile / wall clock), not quoted.

## 0. The headline, skeptically

The scheduling graph is NOT the cost. `ddflow next` = 2.6 s; of that `schedule.plan()` is 0.12 s
(0.40 s under cProfile), `critical_path` 0.02 s, `waves()` over all 1365 live items 0.63 s. The cost is
`_load` = read 65 MB log + `model.fold` = 1.7 s (infra/log.py:1688 `read_all`, core/model.py:335 `fold`).
`ddflow status` = 6.9 s: 4.7 s is `leases.scan` -> 358 git subprocesses over 118 worktrees
(leases.py:1071 `_measure`, infra/worktree.py:444 `tree_work`), 2.8 s of that inside healthwatch.gather;
fold is 1.1 s. So "incremental ready/wave maintenance" would save ~0.1 s of 2.6 s. Do not build it.
The B-perf-* items (P-perf, B-perf-mcp-start "keep the folded State resident by log digest") already
target the true cost. A resident folded State is worth more than any graph cache.

The graph that IS expensive is the Python import graph (section 3): 5.6 s to build for 1487 .py files, no cache.

## 4. Where the current approach is fine (do not touch)

- `core/graph.py` itself (stdlib, iterative, cycle-guarded, tested vs networkx).
- `plan()` readiness at 0.12 s on 2.7k items; `critical_path` 0.02 s.
- Pairwise glob overlap for offers: bounded by slots.
- Decision applicability: glob scope plus enforcement rank is structural and explainable.
- Hop-bounded, hub-cut test reach as a precision/recall policy (the cost is the build, not the walk).
- Doc chunker, similar/dupes (TF-IDF is the right tool for text).

## 5. Open questions I could not settle in the time box

- `ddflow tests` wall time (0.7 s was only `--help`); I measured `build()` directly (5.64 s) but not the whole select path nor whether gates cache the result between ci and unit_tests gates.
- Whether `ddflow brief`/`recall` build their TF-IDF index per call (not profiled).
- Whether any `wave:N` tag consumer exists in ddflow itself (grep found none; they are operator-only).
